Building a bare-metal web browser that boots directly from your UEFI menu—skipping Linux/Windows entirely—is theoretically possible, but practically non-viable for modern web browsing. 

While Inkbox’s assembly project worked because an arcade game only requires low-level graphics buffers, timers, and basic input, a web browser relies on an enormous amount of OS-level infrastructure that UEFI simply does not provide.


Why a True Bare-Metal Browser Doesn't Work

To load a modern website (even a basic one), your hardware program must provide:

A Complete Network Stack: UEFI includes minimal network protocols (PXE/HTTP boot), but lacks full TCP/IP socket management, DNS resolution tools, and modern TLS/SSL encryption libraries (required by almost every HTTPS website today).
A Full Layout & JS Engine: Modern browsers (Chromium, Gecko, WebKit) are millions of lines of C++ code. Rendering HTML, CSS layout trees, and executing JavaScript requires advanced memory management, multi-threading, and system calls that do not exist without an OS kernel.
GPU Drivers: UEFI GOP (Graphics Output Protocol) only provides a basic software frame-buffer (unaccelerated rendering). Browsers rely heavily on GPU hardware acceleration (WebGL, canvas, CSS animations) via Direct3D, Vulkan, or OpenGL.


How to Achieve a "Zero-Friction Bare-Metal" Experience

If your goal is a dedicated boot option in GRUB/systemd-boot that launches straight into a web browser with minimal bloat, fast boot times, and zero UI friction, there are two realistic ways to set this up:

1. Kiosk Mode via a Micro Linux Kernel (Recommended)

You can create a ultra-lightweight custom Linux build that boots straight into a WebKit or Chromium window without running a desktop environment (KDE/GNOME/Hyprland) or display manager.

Boot Time: ~2 to 4 seconds directly to the browser.
Setup: A minimal Arch or Alpine Linux base running a lightweight display server (like Wayland via cage or sway locked to full screen) that launches chromium --kiosk <URL> as the initialization process.
Result: It feels identical to a dedicated bare-metal appliance, but retains hardware acceleration and full web compatibility.

2. Embedded/Minimal Web Runtimes

If you are building a custom C++/Rust application and want embedded web capabilities without a full OS stack, tools like Servo (a parallel web engine written in Rust) or minimal kernels like IncludeOS can be targeted for minimal runtime environments. A "Kiosk OS" isn't a new kernel architecture. It’s a standard Linux kernel stripping out everything in user-space.

What a Linux System Actually Is

When a machine boots Linux, it boils down to two distinct parts:

Kernel Space (vmlinuz): The driver engine. It mounts hardware, manages memory, initializes CPU threads, and exposes /dev handles.
User-Space (init): The very first program the kernel runs once hardware initialization completes.

On a standard desktop (Arch, Ubuntu, Fedora), the kernel boots and hands control over to systemd (pid 1). Systemd launches dozens of background daemons (NetworkManager, Pipewire, Bluetooth, Polkit), a display manager (GDM, SDDM), a window manager/compositor (Hyprland, GNOME, Sway), and finally your user environment.


What Makes a "True Minimal" Kiosk

A true minimal Kiosk OS strips away 95% of that stack:

[ Hardware ] ➔ [ Bootloader (GRUB/systemd-boot) ] ➔ [ Linux Kernel ] ➔ [ Init Script ] ➔ [ Compositor + Browser ]

There is no systemd, no desktop shell, no login manager, no terminal emulator, no panel, and no app switcher. 

The kernel mounts a minimal initramfs system in RAM, executes a basic startup script, initializes a bare Wayland display compositor (like Cage), and immediately launches Chromium directly into the frame buffer.

If Chromium crashes, the system script loops and re-launches it instantly. If you close Chromium, the system has nothing left to render and reboots.


How to Build a Bare-Metal Kiosk Kernel Parameter

If you already run Arch Linux, you can bypass the desktop stack completely without installing a pre-packaged Kiosk ISO.

You can append an initialization override parameter directly to your kernel line inside your bootloader configuration:

init=/usr/local/bin/kiosk-init.sh

When you select this entry from your boot menu, the kernel initializes hardware and skips systemd entirely, executing your custom shell script as PID 1.

Example Kiosk Init Script (/usr/local/bin/kiosk-init.sh)

#!/bin/sh
# Mount essential virtual filesystems required by the Linux kernel
mount -t proc proc /proc
mount -t sysfs sys /sys
mount -t devtmpfs dev /dev

# Turn off screen dimming/blanking
export WAYLAND_DISPLAY=wayland-0

# Launch Wayland (Cage) running ONLY Chromium full-screen
exec cage -- chromium --kiosk --no-first-run --disable-restore-session-state "https://devpryan.in"

This configuration turns an Arch Linux installation into a single-purpose web appliance. It boots directly from the bootloader into a full-screen web session in under 2 seconds.

The boot process boils down to why hardware can't just run software on its own, and how a Kiosk strips away everything except the bare essentials.


Why Can’t the Power Button Just Load the Software?

Pressing the power button is purely a hardware electrical signal—it doesn't know what software, code, or disk exists. 

Think of your computer components like a dark factory with thousands of workers (CPU, RAM, GPU, Disks) who have severe amnesia every time the power turns off:

The Power Button (The Master Switch): Sends electricity through the motherboard.
Firmware / UEFI (The Alarm / Night Watchman): The CPU wakes up in a dumb state and can only read a tiny chip soldered to the motherboard (UEFI). The UEFI does a quick hardware health check (POST) and asks: "Where is the bootable storage?"
The Kernel (vmlinuz) (The Manager): UEFI finds your disk, loads the Linux Kernel into RAM, and hands over control. The kernel initializes all drivers—it talks to the GPU to set up screen output, powers up the Wi-Fi card, and sets up memory management.
Init / systemd (The Boss / Process #1): Once the kernel initializes the hardware, it needs to start running user programs. It launches PID 1 (Process ID 1).

Without the kernel acting as the manager, your software would have no idea how to send a pixel to your specific display monitor or transmit a packet over your specific Wi-Fi chip.


What is systemd's Role?

On a normal system (like standard Arch or Ubuntu), systemd is PID 1. It acts like a company manager who comes in and hires a massive crew:

NetworkManager (for Wi-Fi)
Pipewire/ALSA (for Audio)
Bluetooth daemons
SDDM/GDM (Login screen)
Hyprland/GNOME (Desktop environment)
Apps (Kitty, Firefox, Spotify)

All of these daemons take extra memory and CPU power to boot up and keep running in the background.


What is a Kiosk OS, Exactly?

A Kiosk OS is literally just a standard Linux kernel where you fire the manager (systemd) and hire a single worker instead.

Instead of launching systemd to load 50 background services, desktop shells, panels, and login screens, the kernel launches one script as PID 1.

Normal Linux Boot:
[ Firmware ] ➔ [ Kernel ] ➔ [ systemd ] ➔ [ 50+ Daemons / Desktop ] ➔ [ Browser ]

Kiosk Boot:
[ Firmware ] ➔ [ Kernel ] ➔ [ One Init Script ] ➔ [ Wayland + Browser ]

Why Distrobox / Containers Don't Work for This

Distrobox and Docker run inside an already booted OS—they sit on top of your existing kernel, display server, and systemd stack. 

To test this safely without touching your daily driver setup:

Test in a Virtual Machine (QEMU / KVM): Create a blank VM, attach an ISO like Porteus Kiosk, and boot it. You get to see the sub-3-second boot time and locked-down browser experience in a sandbox.
Dedicated USB Drive: Flash a Kiosk image directly to a spare USB stick. Booting off the USB leaves your main internal SSD completely untouched.

# (Creates lightweight bootable image via mksquashfs/grub-mkrescue)

Strategy 2: Image-Based A/B Atomic Updating (Solving the Update Problem)

If you strip a machine down to a single bare-metal image, traditional package updates (apt update or pacman -Syu) break because there is no package manager or standard system shell.

The industry standard for updating stripped-down bare-metal devices (kiosks, Tesla car dashboards, steam decks, embedded systems) is Atomic A/B Partitioning.

Disk Drive Layout:
[ Bootloader (GRUB) ] -> Points to Active Partition

Partition A (Active / Read-Only):  [ Current OS + App 1 + App 2 ] (Running)
Partition B (Inactive / Writing):  [ Downloaded New Base Image   ] (Updating)

How the Update Workflow Works:

Read-Only Runtime: Partition A is marked completely read-only (OverlayFS). The running apps cannot modify system files, protecting against corruption.
Background Download: When an update releases, the system streams a single pre-compiled binary image file (built on your dev machine) straight into Partition B.
Atomic Swap: Once Partition B passes cryptographic signature checks, the bootloader flips the active flag to Partition B and reboots.
Instant Rollback: If Partition B fails health checks on boot, the hardware instantly reboots back into Partition A. Zero bricked devices.
